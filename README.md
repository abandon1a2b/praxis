# PRAXIS

An extensible autonomous agent system

Praxis 是一个通用、可扩展、可长期运行的自主 Agent 系统。

**发现值得做的事情，自主获取能力，完成事情，并验证真实结果。**

终极愿景是构建一个能够承担原本需要大量人员协作才能完成的工作的通用自主 Agent 系统，即“1 代替 100”。这是愿景表达，具体能力须通过真实工作验证。

## 项目宪章 v0.1

**理念大于工具，大于框架，大于实现。**

理念决定系统为什么存在、要解决什么问题，以及如何判断结果是否有价值。工具、框架和具体实现都服务于这一理念，可以随着需求和实践反馈调整、替换或重构。

**Praxis 不应该依赖我们永远比 AI 更懂得如何做事，而应该为 AI 终有一天比我们更懂得如何做事做好准备。**

Praxis 的核心是知行合一：理解目标，落实行动，验证结果，再用反馈指导下一次行动。技术选型应当由这个过程的需要来决定。

Praxis 的目标不是模仿人类如何分工，而是让事情以更低成本、更少人工介入、更可靠的方式真正完成。

### 核心原则

1. **Outcome over Process**：以真实结果为目标，而非任务执行过程。
2. **Capability over Role**：以能力组合解决问题，而非预设职业角色。
3. **Autonomy over Workflow**：长期由 Agent 自主规划和行动；前期允许明确配置执行内容与触发条件，随基础能力成熟逐步扩大自主决策范围。
4. **Reuse over Reinvention**：优先复用成熟 Harness、模型与工具。
5. **Verification over Assertion**：完成声明不等于目标达成，必须有可信验证。
6. **Evolution through Practice**：从真实任务中持续积累可复用能力。
7. **Safety by Architecture**：权限、审批、资源预算和审计由平台独立约束。

## 项目状态

项目目前处于基础实现阶段。已接入 Pi，并实现业务代码检查、配置驱动的本地控制服务及 React + shadcn Web 控制台。自主观察与规划、外部事件及通用插件接口尚未实现；本 README 中的长期方向不代表相关能力已经具备。

这份定义作为初始项目宪章。近期先建设配置驱动的运行基础，结合 Pi 的实际能力确定最小架构，自治能力在基础组件和整体运行达到一定成熟度后推进。

### 近期建设方向

近期形态是配置驱动、可长期运行的 Agent 系统：用户配置执行内容、模型、工作目录、定时或事件触发条件及操作约束，系统在条件满足时调用 Harness，并保存运行状态与执行记录。

自动运行与自主决策分阶段建设。前期由人明确执行内容和边界，系统负责可靠触发、执行和记录；后期再逐步引入自主观察、发现问题、规划和优先级判断。CLI 可用于启动和调试，核心交付是配置后的持续运行能力。

首个可运行版本先打通“加载配置 → 常驻等待 → 定时触发 Pi → 保存执行状态与结果”，同时建立必要的并发、超时、失败处理和重启恢复机制，再逐步接入外部事件。

## 为什么叫 Praxis

Praxis 意为实践、行动与知行合一，强调把目标转化为行动，并以实际结果验证行动是否有效。

这个名字对应项目的基础价值：可靠地完成任务。即使未来不实现持续学习或业务 Agent 衍生，Praxis 仍然成立。

| 长期运行   | 支持事件触发、周期唤醒、持久化状态、暂停和任务恢复，不要求模型持续推理                             |
| 能力扩展   | 通过插件、SDK、MCP、API 接入外部系统，在授权范围内开发新工具                                       |
| 记忆与知识 | 持久化目标、环境认知、历史决策、执行经验、工具能力及验证结果                                       |
| 配置       | 前期配置执行内容、模型、工作目录、触发条件及约束；逐步支持目标、能力、资源与权限的可视化配置       |
| 工作流定位 | 可选能力，非核心概念，不要求用户预先定义工作流程                                                   |
| 任务管理   | 前期管理配置的工作及其运行实例，后期逐步支持动态生成、拆解、执行和调整任务                         |
| 结果验证   | 区分任务完成与目标达成，支持测试、指标、外部反馈和独立验证                                         |
| 持续演进   | 从真实执行中发现能力缺口，积累可复用知识、工具和策略                                               |
| 权限与安全 | Agent 自主决策，平台独立控制权限、预算、审批、隔离、审计与停止条件                                 |
| 资源效率   | 减少 Token、计算资源和人工介入成本，避免无意义的自主循环                                           |
| 部署形态   | 优先考虑可独立部署、插件化、可配置、可长期运行                                                     |

## 技术路线

复用成熟的 Agent Harness 作为执行基础，先在其上建设配置、调度、运行管理、持久化和执行记录，再逐步完善能力接入、任务管理与结果验证。具体实现根据执行可靠性、可扩展性和实际业务需求调整。

Pi 已作为首个 Harness 接入并验证模型调用，是否长期采用由后续实践决定。OpenCode、Codex 等保留为评估候选。接入边界保持清晰，避免依赖执行引擎的私有实现，按实际需要渐进完善适配层。

保持领域无关，允许动态委派但不强制采用多 Agent 架构。优先使用最小可行架构，避免过早抽象和复杂化。

设计遵循以下原则：

- 优先复用成熟基础设施，把投入集中在任务执行和业务价值上。
- 明确任务目标、操作边界和验收标准，让执行过程可追踪、结果可检查。
- 通过插件组织业务能力，保持核心系统与具体业务之间的清晰边界。
- 以实际任务中的反馈决定能力改进，避免仅凭经验记录就宣称系统完成了学习。

| Persistent State       | 配置关联、运行状态、执行进度与重启恢复                   | P0         |
| Execution Records      | 记录模型输出、工具调用、错误、资源消耗和执行结果         | P0         |
| Policy & Permission    | 基础操作边界、资源上限与停止条件起步，逐步完善权限及审批 | P0         |
| Capability System      | 工具注册、发现、调用、插件接入                           | P1         |
| Goal & Task System     | 工作与运行实例管理，逐步完善目标及任务管理               | P1         |
| Verification System    | 在执行状态与结果记录基础上，验证实际效果和目标达成       | P1         |
| Memory & Knowledge     | 长期知识检索、经验沉淀、上下文构建                       | P1         |
| Observation & Autonomy | 主动观察、发现问题、自主规划及优先级调整                 | P2         |
| Evolve System          | 发现能力缺口、改进工具、沉淀可复用能力                   | P2         |
| Web Console            | 可视化配置、运行监控、审批和结果查看                     | P2         |

优先级仅表示建议实现顺序。模块表是初步职责划分，不是开发任务清单，也不要求每个模块成为独立服务。实际边界和实现顺序应在评估 Harness 能力及场景需求后确定。

## Evolve：可选的能力演进模块

Evolve 负责探索如何将任务执行中的反馈转化为可复用、可验证的能力。

| 职责            | 目标                                         |
| --------------- | -------------------------------------------- |
| 经验沉淀        | 保存问题背景、处理过程、结果及适用条件       |
| 能力提炼        | 从重复任务中提炼可复用的知识、工具或工作流程 |
| 验证与迭代      | 检查改进是否有效，再决定是否纳入可用能力     |
| 业务 Agent 衍生 | 在未来探索将成熟业务能力组合为专用 Agent     |

Praxis 是整个项目，Evolve 是其中一个可选模块。可靠执行是基础，能力演进建立在执行反馈和验证机制之上。

Evolve 的成立需要实际证据：系统应当能够通过反馈改善后续任务表现。记录经验、生成工具或生成 Agent 本身，并不等于能力已经提升。

## 当前边界

- 近期先建设配置驱动的自动运行基础，自主发现与规划在基础组件和整体运行成熟后推进。
- 自主进化和业务 Agent 生成属于探索方向，尚未决定具体实现。
- Evolve 不作为核心执行能力成立的前提。
- 当前提供本地单用户控制台；更完整的部署和能力配置随实现逐步补充。

## 本地开发

需要 Node.js 22.19 或更新版本，推荐 Node.js 24。在项目根目录安装依赖并启动控制台：

```sh
npm ci
npm run dev
```

默认打开 `http://127.0.0.1:4310`，在页面创建业务，填写本地 Git 仓库的绝对路径、检查范围和目标。启用定时检查并保存后，系统按间隔触发；也可手动检查。`PRAXIS_PORT` 可指定端口，`PRAXIS_DATA_DIR` 可指定控制服务数据目录。生产模式先执行 `npm run build`，再执行 `npm run serve`。

模型提供商认证可通过 Pi 的 `/login` 配置，也可使用本机已有凭据或自定义服务配置。认证信息保存在本机，不应提交到仓库。可通过 `npm run pi -- --help` 查看命令参数。

`npm run pi` 仍可启动原生 Pi CLI 进行调试。控制层源码在 `src/control/`，执行边界在 `src/harness/`，页面在 `src/web/`。配置版本和独立运行实例存储于 `.praxis/control.sqlite`，检查缓存存储于 `.praxis/cache/`，均不提交到仓库。数据所有权、调度和恢复语义见 [架构说明](docs/architecture.md)。

验证命令为 `npm test`、`npm run build` 和 `npm run test:ui`。浏览器测试需要 Playwright Chromium（`npx playwright install chromium`），也可通过 `PRAXIS_CHROME_PATH` 指定本机 Chrome 可执行文件。

## 首个能力：业务代码检查

### Agent 接入

通用开发任务已通过 `/api/tasks` 接入 Pi 原生 read/bash/edit/write/grep/find/ls；配置 `resources=true` 时加载原生项目指令、skills、prompt templates、扩展及 MCP/codemode/tool_search。资源默认关闭，显式信任后开启。通过任务的 `/messages` 追加指令、`/resume` 续接会话、`/cancel` 取消执行。请求格式和全部接口说明读取 `/api/docs`。

开发任务使用真实工作目录，具有当前系统账号权限，尚无 OS 沙箱；它与只读代码检查是不同的执行模式。页面提供业务检查及通用任务轨迹，通用任务的创建和控制通过 API 操作。`npm run verify:pi` 在临时项目中实测编辑、测试、项目资源、MCP、追加指令和会话续接，不修改业务仓库。

页面侧栏的“任务轨迹”可查看通用任务历史、模型回复、工具参数与输出、错误和追加指令；业务检查报告也有“执行轨迹”标签。轨迹从 Pi 原生日志读取，运行中自动更新，最多展示最近 200 条事件，每项详情最多 20,000 字符；不展示模型内部推理。旧运行无原生日志时显示空记录。通用任务的创建与控制目前仍通过 API 完成。

提供短 skill：[skills/praxis/SKILL.md](skills/praxis/SKILL.md)。其他 Agent 先读取 `GET /api/docs` 获取当前服务的 OpenAPI 文档及调用说明，再通过控制 API 配置业务、触发检查和查询结果。接口文档由实际路由定义和 Zod 请求校验 schema 生成，不维护独立的静态参数清单。

将 `skills/praxis/` 目录放入 Agent 的技能目录即可使用；skill 不绑定业务仓库、公司或模型提供商。

Web 控制服务默认使用完整 Pi Agent 会话：授权范围的 Git 跟踪文件形成固定代码快照，Agent 使用 Pi 原生 read、grep、find、ls 工具按需探索、追踪跨文件契约，启用原生上下文压缩及有限重试。每次运行独立保存会话、工具事件和结果，提供检查总时限及取消；扫描阶段也响应取消。禁用写入、shell、扩展及项目指令加载，Agent 无法调用控制层配置写接口。

覆盖报告记录文件读取和截断情况，不把“读过文件”视为“全量语义检查完成”。目前尚未保证整个大型业务的全量检查；总时限内的探索结果必须复核。原始业务文件保持不变，模型只访问不含常见凭据文件的临时快照。执行进程仍非 OS 沙箱。

可运行 `npm run compare:harnesses` 与本机 Codex 做同模型、同样例对照；最新验证条件、失败记录和结论见 [原生 Harness 对照](docs/harness-comparison-2026-10-09.md)。

以下文件配置入口保留旧分批检查方式，仅用于调试与对照，不是 Web 默认执行路径：

```sh
# 单次验证
npm run review -- examples/code-review.json --once
# 常驻运行：启动时检查，此后在每次执行结束后等待配置的间隔
npm run review -- examples/code-review.json
npm test
```

复制示例配置并调整仓库路径及范围；相对仓库路径以配置文件目录为基准。省略 include 时扫描全部 Git 跟踪文件，未跟踪文件不在范围内。二进制、符号链接及常见凭据文件跳过；仍需自行排除包含敏感数据的业务文件。报告与进度保存在 `.praxis/runs/<业务 id>/`，`latest.json` 包含完成批次、代码版本、跳过范围及问题列表。

问题必须包含有效文件位置、触发条件、影响说明和对应行的原文证据。证据校验只验证引用准确性，不等于问题成立；模型结果仍需复核。当前为分批代码审查，不执行测试，不修改代码，不承诺跨模块完整分析；completed 仅表示配置范围内批次处理完成。相同快照会复用已完成结果，代码或配置变化后生成新检查。快照来自工作区文件，扫描时应避免并发改动代码。

上面的 `npm run review` 是保留的文件配置调试入口，记录存放在 `.praxis/runs/`，正常退出在当前运行结束后停止；异常退出的锁需确认无活跃进程后手动移除。日常运行使用 Web 控制服务，拥有独立配置版本和运行历史，支持取消及重启中断恢复。暂未实现日历 cron 或外部事件。

## 明确的非目标

| 不做什么                     | 原因                                                              |
| ---------------------------- | ----------------------------------------------------------------- |
| 不从零开发大模型             | 复用现有模型能力                                                  |
| 不从零重造成熟 Harness       | 集中精力建设通用自治能力                                          |
| 不以工作流编排为中心         | 前期允许配置明确工作，长期逐步扩大 Agent 对执行过程的自主决策范围 |
| 不预设 CEO、程序员等固定角色 | 以能力和目标为中心，而不是模仿组织结构                            |
| 不限定软件开发场景           | 保持跨行业的通用性                                                |
| 不追求 Agent 数量            | 关注实际完成的工作                                                |
| 不以执行成功代替结果成功     | 必须验证真实效果                                                  |
| 不允许无限自主执行           | 需要资源、风险与权限边界                                          |

## 初期验证与衡量标准

初期先验证运行基础：

| 能力       | 验证重点                                                                          |
| ---------- | --------------------------------------------------------------------------------- |
| 配置加载   | 配置可校验，执行内容、模型、工作目录与约束正确传入 Harness                        |
| 定时触发   | 按配置时间触发，触发与运行实例可关联，重复触发及并发行为明确                      |
| 执行与记录 | 能调用 Pi，持久化状态、输出、工具调用、错误与结果；执行成功与业务目标达成分开记录 |
| 运行控制   | 并发上限、超时、取消、资源限制及失败处理按约定生效                                |
| 重启恢复   | 重启后可读取历史状态，识别中断运行，按明确策略处理漏触发和未完成执行              |
| 事件接入   | 定时运行基础稳定后，验证外部事件触发、去重及失败处理                              |

运行基础稳定后，优先从代码质量和问题排查两个场景验证业务效果：

| 场景     | 工作目标                                                       | 验证重点                                                 |
| -------- | -------------------------------------------------------------- | -------------------------------------------------------- |
| 代码质量 | 识别有证据的缺陷、测试缺口和维护风险，提出或实施改进           | 通过测试和实际行为验证效果，关注缺陷减少和维护成本       |
| 问题排查 | 从报错、失败测试或异常现象出发，收集证据、复现、定位原因并修复 | 验证问题得到解决，关注定位准确率、解决时间和人工介入次数 |

先形成配置、触发、执行、记录和恢复的运行闭环，再完善业务结果验证与能力接入，最后逐步推进自主观察、判断、规划及经验演进。软件工程是首个业务验证领域，通用自治能力仍是长期方向。个人日常工作自动化和 GooseForum 的维护与改进作为后续扩展场景。

首要落地目标是在真实、获得授权的工作环境中，逐步降低人的日常介入比例，覆盖工程、产品、设计、监控、运营及其他实际工作。

长期评价标准是：在明确的质量、成本、风险和权限约束下，系统能够独立发现并完成多少有价值的真实工作，以及节省多少人工投入。
