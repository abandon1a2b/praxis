# 检查计划、复核与恢复

## 目标与约束

控制层拥有检查范围与进度，Harness 只能执行指定阶段和提出候选问题。每次运行独立记录；相同配置及源码快照可接续工作。保持原生只读工具，不给模型修改配置或业务代码的能力。

## 已验证问题与先前方案

最初分批文本审查缺少跨模块探索；随后单次原生 Agent 探索改善工具访问，但一次 JSON 输出不能证明业务全量覆盖，超时后下一运行从头探索。此前实现见 5587f6d、caf9e29 及 native-agent-integration.md。读取事件只代表访问，不证明语义检查完整，这是已验证的接口限制。

## 当前方式

控制层按仓库和一级目录形成模块，按字符预算拆分范围，包含长行列片段。结构理解、模块检查、跨模块检查与逐问题复核分阶段执行。模块输入附带指定范围的编号原文，避免原生 read 截断造成该范围没有进入模型上下文；同时要求本批访问指定文件以支持依赖探索。全文语义覆盖仍不能由读取事件或 JSON 声明证明。

检查计划带版本，缓存键包含执行配置及源码内容，不依赖 Git dirty 标志。阶段完成时原子写入 checkpoint，失败只重试未完成阶段。工作区每次重新构造、结束后删除，缓存不保存源码。全局单执行约束保障 checkpoint 无并发写入。改变模型、目标、范围或源码会失效；升级执行协议需升级 PLAN_VERSION。

候选问题保留原文定位校验，另起模型会话挑战问题，记录 confirmed/rejected/needs-context。confirmed 只表示静态模型复核支持，未执行复现测试；不能宣称独立验证或运行时确认。

## 验证与残留风险

tests/review-plan.test.js 验证计划范围、失败后跨运行接续、问题状态保留和源码变更失效；native-review.test.js 验证原文及只读边界；web.spec.ts 验证计划展开及复核标签。相关实现为 src/agent-review.js、src/review-plan.js。

目录分组不是语义模块分析；结构摘要、跨模块探索及静态复核仍依赖模型。极大清单和候选集合尚需分页或分层归并。单运行总时限可能不足以完成阶段，下一次触发续跑；单阶段持续超时需要更细分阶段。缓存无自动过期、清理和强制复查。上层目录及同账号访问仍不是 OS 沙箱。

从零重构应先定义覆盖证据层次、阶段预算、内容寻址缓存协议、模型复核和实际复现的区别，以及恢复与原运行记录的关系。回归需覆盖空输出、无读取、错误引用、长行截断、阶段取消、源码变化、缓存损坏和并发控制，避免把输出成功等同于目标达成。
